# 仕様: 繰り返しタスクと期限リマインド

- ステータス: 実走用に確定（2026-09-05。書籍完成・検証・マージの委任に基づきCodexが未決事項を補完）
- 対象: `src/types.ts` / `src/store.ts` / `src/notify.ts` / `src/server.ts` および新規 `src/recurrence.ts`

## 1. 最初の要求（人間から出た一文）

> 繰り返しタスクと期限リマインドを追加したい。

この一文はこのままではAIチームに渡せない。**渡せない理由は、実装が難しいからではなく、完了条件が判定できないから**である。以下は、この一文を渡せる単位に刻む作業の記録。

## 2. 曖昧さの洗い出しと決定

要求から機械的に取り出した「決めないと実装が分岐する点」と、その決定。

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 繰り返しの表現力 | `daily` / `weekly` / `monthly` + `interval`（1以上）のみ。iCal RRULE は非対応 | ランタイム依存ゼロの前提を守る。表現力を上げても題材としての学びは増えない |
| 2 | 次インスタンスの生成タイミング | **完了時に1件だけ生成**。先行生成しない | インメモリ前提で無限生成を避ける。「未完了が1件だけ存在する」という不変条件が単純 |
| 3 | 月末の扱い（1/31 の毎月繰り返し） | 存在しない日はその月の最終日に丸める（1/31 → 2/28）。**ただし元の日を `anchorDay` として保持し、翌月以降は31に戻す** | 丸めた日を次回の基準にすると 1/31 → 2/28 → 3/28 と繰り上がって二度と31に戻らない。この挙動は利用者の期待と食い違う |
| 4 | 遅延して完了した場合の次回期限 | **元の期限を基準**に進める。ただし結果が過去日になる場合は、未来日になるまで繰り返し進める | 完了日基準にすると、遅れるたびに予定全体がずれていく |
| 5 | 「完了」の単位 | インスタンス単位。同一シリーズは `seriesId` で束ねる | シリーズ単位の完了は「繰り返しの停止」であり、別の操作（#6）として扱う |
| 6 | 繰り返しの終了条件 | `until`（YYYY-MM-DD）と `count`（回数）を任意で指定可。両方未指定なら無期限 | 無期限しかないと止める手段がない |
| 7 | タイムゾーンと現在時刻 | **日付計算は現在時刻を参照せず、`today`（YYYY-MM-DD）を引数で受け取る**。決定 #4 のために `complete(id, today)` へ引数を追加する（未指定時は `new Date()` から導出して後方互換を保つ）。`createdAt` / `completedAt` が `new Date()` を使う既存挙動は変更しない | 既存の `buildDailyDigest(store, today)` と同じ設計。日付計算だけ決定的にすればテストが書ける。TZ変換自体は呼び出し側の責務のまま |
| 8 | リマインドの通知回数 | 日次ダイジェストに「N日以内に期限」セクションを追加するのみ。「通知済み」の状態は持たない | 状態を持つと冪等性が壊れる。ダイジェストは何度呼んでも同じ結果になるべき |
| 9 | 永続化 | 追加しない。インメモリのまま | 既存の設計前提（`CLAUDE.md`）を壊さない |

**決定 #3 と #4 が、この題材で最も間違えやすい2点**。どちらも「動くコード」は簡単に書けるが、仕様が曖昧なままだと異なる解釈の実装になり得る。

## 3. 完了条件（Definition of Done）

### 3.1 機械判定できる条件

- `npm run typecheck` / `npm test` / `npm run lint` がすべて成功する
- `package.json` の `dependencies` が空のままである（ランタイム依存ゼロ）
- **既存テストが1件も変更されていない**（期待値を書き換えてエラーを消していない）
- 以下のテストケースが新規に存在し、成功する:
  - 毎月・1/31 起点 → 2/28 → 3/31（決定 #3 の anchorDay 保持）
  - うるう年: 毎月・1/29 起点 → 平年の2月は 2/28、うるう年の2月は 2/29、いずれも翌月は 3/29 に戻る
  - 毎週・interval 2 の隔週
  - 遅延完了: 期限を10日過ぎて完了 → 次回期限が `today` より後になるまで進む（決定 #4）
  - `count` 到達時・`until` 超過時に次インスタンスが生成されない
  - 繰り返しなしのタスクを完了しても新規タスクが生成されない（既存挙動の回帰）
- API 契約:
  - `POST /tasks` が `recurrence` を受け付け、不正な値には 400 を返す
  - `GET /tasks` の各タスクが `seriesId` を持つ（繰り返しなしは省略）
  - `GET /digest` に「N日以内に期限」セクションが含まれる

### 3.2 機械判定できない条件（人間が見る）

- 命名と責務分割が既存コードの流儀に沿っているか
- 日付計算が `src/recurrence.ts` に純関数として閉じているか（`store.ts` に散らばっていないか）
- `complete()` のシグネチャ変更が既存の呼び出し元（`server.ts`）を壊していないか

**人間の判断に残す条件を明確にすることも、要件定義の仕事である**。たとえば「anchorDay を保持する」は当初「月末の扱いが自然であること」という人間判定の条件だったが、決定 #3 で仕様を確定させたことでテストケースに落ち、機械判定側へ移った。

## 5. 実走前の補完（2026-09-05）

元の仕様で未決だった入力境界と再実行の契約を、次のように定める。ユーザーがこの細部を逐一指定したという記録ではなく、書籍と実装を完成させる委任の範囲での設計判断である。

- `Recurrence` は `frequency`（daily / weekly / monthly）、`interval`（1〜10,000の整数）、任意の `count`（1〜10,000の整数）と `until`（実在する日付）を持つ。未知のキー、null、配列、型の違いは拒否する。
- 日付は0001-01-01〜9999-12-31の実在するグレゴリオ暦日付に限定する。日付文字列の比較と計算はUTCの暦日として扱い、現在日付の省略時もUTCから導出する。地域別タイムゾーン変換は追加しない。
- 繰り返しには期限が必須。`until` は最初の期限以上の日付を指定し、次回期限の上限とする。当日を含む。
- `count` は最初のタスクを含む生成総数。過去日を飛ばしても、生成していない予定は回数に数えない。各タスクに `occurrence`（最初は1）を保持する。
- `complete(id, today?)` は既存どおり完了したタスクを返す。次回タスクは `list()` で確認できる。同じIDの二度目の完了は既存どおりエラーとし、二重生成しない。
- 次回期限は、現在の期限からintervalの周期を保ち、`today` より厳密に後の日へ進める。月次のanchorDayはシリーズの最初の期限の日を保持する。
- 範囲を超える日付計算や不正入力で失敗する場合は、現在のタスクを完了状態に変えない。count / untilで終了する場合は正常に完了し、次回を生成しない。
- `buildDailyDigest(store, today, withinDays = 3)` は、今日より後、today + withinDays以下の未完了タスクを「N日以内に期限」に列挙する。期限切れ・今日・期限なし・完了済みはこの欄に含めない。該当なしは「- なし」、withinDaysは0〜365の整数。本文生成による状態変更・外部送信は行わない。
- `POST /tasks/:id/complete?today=YYYY-MM-DD`、`GET /digest?today=YYYY-MM-DD&withinDays=N` を受け付ける。不正値は400。既存のクエリ省略時の呼び出しは維持する。
- `handle()` が返すHTTPサーバー間でストアを共有しない。テスト用にストアを注入できる構成を許す。

### 追加した受け入れ確認

- 未知のrecurrenceフィールド・存在しない日付・小数や負数のinterval/countを拒否する。
- count=1では次回を作らない。遅延で予定日を飛ばしても生成数だけを数える。
- until当日は生成し、超えたら停止する。日付上限の失敗でも完了状態と件数を変えない。
- 同じ完了要求を再送しても、同一シリーズの未完了が重複しない。
- リマインドの両端・月またぎ・対象外のタスク・同じ入力での再生成を確認する。
- HTTP経由で作成→完了→次回生成→ダイジェストを確認し、不正入力の400と状態不変も確認する。

- ダイジェストの窓の終端が9999-12-31を超える場合は、この最終日までに制限する。
